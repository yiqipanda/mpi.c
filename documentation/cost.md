# Time and memory cost of process partitioning

## Evidence and limits

This analysis describes the `temp_src/` matrix demo and the single run recorded in [`logs/syslog.log`](../logs/syslog.log). The main process builds two 4 × 4 matrices, creates one `MatrixMultiplication` object, splits its right operand by columns, and sends the **full** operation to worker 1 and the two halves to workers 2 and 3. It then asks for the full result first, retrieves both partial results, joins them, and checks equality. See [`main_process.py`](../temp_src/main_process.py), [`matrix.py`](../temp_src/matrix.py), and [`other_process.py`](../temp_src/other_process.py).

The log contains wall-clock event timestamps and worker-side `perf_counter()` evaluation durations. It contains no process memory samples, GPU run, local single-process baseline, or separate timers around object creation, partitioning, serialization, result decoding, or orchestration. Numbers below are labeled as **measured**, **derived from code**, or **unmeasured** accordingly. The first-to-last log interval ends before final log formatting and disk write, so it is not the complete script runtime. A single run does not establish variability.

The **measured logged span** from main start (line 1) to the final acknowledgment event (line 74) is **1.658511 s**, conventionally **1.659 s**. It includes worker registration, the full comparison computation, result handling, and logged log collection. It does **not** measure a partition-only completion time. The full worker is the critical path because the main process waits for its result first. Merely halving each worker's evaluation duration does not halve this demo's logged completion time.

### Why the evaluation figures need care

`MatrixMultiplication._dot_product()` calls `time.sleep(0.1)` once for **every output entry**. A 4 × 4 product therefore has 16 sleeps, or at least **1.6 s** of requested sleeping; each half has eight, or **0.8 s**. The slower partition's reported evaluation is about **1.96×** faster than the full worker's evaluation (`1.649791 / 0.840207`), close to the twofold difference in sleep count. This primarily demonstrates overlap of waiting in separate processes. It does not measure CPU arithmetic speedup, serialization cost at realistic matrix sizes, or any advantage over a GPU.

## Memory ownership and amplification

Let the left operand `A` contain `M × K` entries, the right operand `B` contain `K × N` entries, and the output contain `M × N` entries. The table counts **matrix entry slots in nested Python lists**, not bytes. In main, row copies and slices make new lists of references to existing scalar objects; decoding a JSON message in another process creates separate list and scalar objects. Python list headers, row headers, integer objects, `MatrixMultiplication` wrappers, dictionaries, messages, sockets, logs, and temporary encoded buffers add more memory.

| Long-lived state in this demo          | Operand entry slots |         Output entry slots | Why it remains resident                                                                                               |
| -------------------------------------- | ------------------: | -------------------------: | --------------------------------------------------------------------------------------------------------------------- |
| Main's original full object            |         `MK + KN` | `MN` after orchestration | `mm1` is retained and later receives the joined result.                                                             |
| Main's two partition objects           |        `2MK + KN` |                          0 | `mm2`, `mm3`, and their messages still reference them. Both partitions hold a copied `A`.                       |
| Three workers' stored objects          |       `3MK + 2KN` |   `2MN` after evaluation | Worker 1 stores a full comparison job; workers 2 and 3 store half jobs. Each retains its input after evaluation.      |
| Main's three returned function objects |       `3MK + 2KN` |                    `2MN` | Result replies include`params` as well as `result`; the `results` dictionary retains all three decoded objects. |

Immediately after main partitions its input, its list slots for operands total **`3MK + 2KN`**, compared with **`MK + KN`** before partitioning. For the 4 × 4 demo this is **80 versus 32 slots, or 2.5×**. Once all three workers have their inputs, main and workers together retain **160 operand slots, or 5×** the original 32. After the result objects return and orchestration completes, retained operands total **240 slots** and retained output slots total **80**, across all processes: **320 matrix entry slots** in this particular comparison demo. This is a code-derived inventory, **not** a measured peak memory value or a ratio of resident bytes. A production partition-only run would omit the full comparison worker and its returned result, reducing these counts.

Transient peaks can be higher. `MatrixMultiplication.serialize()` first calls `json.dumps()` to validate the state; `Message.serialize()` then JSON-encodes the envelope again. The resulting string is UTF-8-encoded to bytes for sending. The receiver holds an input byte line, decoded text, parsed JSON lists and dictionaries, and a restored function object during part of deserialization. Returned functions repeat this path with both parameters and results. Evaluation creates transposed-column tuples and output lists; orchestration creates another set of output rows. The log snapshot/merge/export path also retains and copies log collections. The timing log records no RSS, heap allocation, payload sizes, or allocation lifetimes, so it cannot establish whether a given phase precisely doubles memory or identify the actual peak. **Doubling is plausible at a transfer boundary, but this implementation's persistent and transient duplication can exceed it.**



Constraints: We've used time.sleep to simulate the time load of some functions. IPC is relatively easier than computer-computer communication.
